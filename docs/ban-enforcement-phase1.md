# تقرير الإصلاح: الحظر النهائي الشامل (Phase 1)

**الحالة: ✅ منفَّذ ومُختبَر (8/8 اختبارات جديدة ناجحة + الاختبارات القديمة سليمة 20/20)**

**الهدف:** عند تنفيذ «حظر نهائي» من بروفايل العضو (`profile:adminAction` action=ban) يجب أن يُسجَّل
حظر دائم غير قابل للتجاوز بـ: الاسم، عنوان IP، بصمة الجهاز، توقيع الجهاز — بحيث لا يستطيع العضو
العودة كزائر، أو تسجيل عضوية جديدة، أو تسجيل دخول حسابه، حتى لو غيّر عنوان الـ IP.

---

## 1. المشكلة الحالية (تم التحقق منها)

| السلوك الحالي | الملف / الدليل |
|---|---|
| زر «حظر نهائي» يرسل `socket.emit("profile:adminAction", {action:"ban"})` | `src/components/profile/ProfileAdminPanel.tsx` (سطر 320-332) |
| المعالج يقسم: تنبيه مرئي + `force_logout` فقط — **لا يكتب أي سجل في `moderation_bans`** | `server/socket/profileHandlers.ts` (سطر 579-598) |
| فحص الحظر عند الدخول/التسجيل/الزائر/الاتصال يعتمد حصراً على `moderation_bans` | `server/services/banCheck.ts` ← يستدعيه `authService.ts` (262/419)، `auth/register.post.ts` (16)، `socket/index.ts` (95-105) |
| **النتيجة:** العضو المحظور يعود فوراً بإعادة تسجيل الدخول أو التسجيل مجدداً أو الدخول كزائر | — |

## 2. المعرفات المتوفرة في النظام (المصادر)

| المعرف | يُحفظ في | يُرسل عند كل دخول | يُفحص عند |
|---|---|---|---|
| الاسم (`username`/`target_name`) | `users.username` | نعم | دخول العضو + دخول الزائر (نفس الاسم) |
| IP | `users.ip` (يُحدَّث في كل دخول عبر `storeDeviceInfo` — `authService.ts` 224-248) | نعم (x-forwarded-for / getSocketIp) | دخول العضو + الزائر + التسجيل + اتصال السوكيت |
| بصمة الجهاز | `users.fp` | نعم (`getDeviceId` → `socket.ts` 58 / `useAuth.ts` 65 / headers) | نقاط الدخول الأربع كلها |
| توقيع الجهاز | `users.device_signature` | نعم (`getDeviceSignature`) | نقاط الدخول الأربع كلها |

مخطط `moderation_bans` يدعمها أصلاً (سجلات مستقلة لكل نوع حظر):
`ban_type ∈ {name, ip, device}` + `ip_address` + `device_fingerprint` + `device_signature`
(`server/db/migrate.ts` 1529-1548، `server/routes/api/admin/bans.post.ts` كنموذج للكتابة الصحيحة).

**الخلاصة:** تغيير الـ IP لا يفيد العضو المحظور لأن حظر بصمة/توقيع الجهاز يبقى ساري matcher في
`banCheck` مستقلاً عن الـ IP؛ وتغيير الاسم لا يفيد لأن حظر الجهاز يعمل. السيناريو الوحيد غير المغطى
هو جهاز/متصفح مختلف تماماً + IP مختلف — وهذا خارج نطاق آلي بصمات الجهاز نفسه.

## 3. الحل المُنفَّذ

### 3.1 خدمة جديدة: `server/services/profileBanService.ts`
دالة `applyPermanentSiteBan({ targetProfile, actorId, reason, pool? })`:

1. جلب صف الهدف من `users`: `id, username, ip, fp, device_signature, idreg, uid`
   (بحث بكل المعرفات: id/uid/idreg/username).
2. **حمايات:** رفض حظر مالك الموقع (`isSystemOwnerUsername`)، رفض إذا لم يوجد هدف.
3. بناء خطة السجلات (بدون تكرارات — تُفحص السجلات النشطة الموجودة أولاً):
   - `name` حظر باسم العضو.
   - `ip` حظر بآخر IP معروف، `decoder_code = ip`.
   - `device` حظر بالبصمة/التوقيع (صفاً معاً بصف واحد إذا وجدا، يغطي `banCheck` كليهما)، `decoder_code = fingerprint`.
4. كتابة السجلات إلى `moderation_bans`: `is_active=true`، `expires_label='دائم'`، `expires_at=null` (دائم)،
   `created_by = actorId`، `reason`.
5. تدقيق: `logModerationEvent({ eventType: "site_ban.permanent", ... })`.
6. الإرجاع: `{ banned, name, ip, deviceFingerprint, deviceSignature, skipped, deniedReason? }`
   ليعرف المشرف بان أي معرفات التُقط فعلياً.

### 3.2 تعديل `server/socket/profileHandlers.ts` (فرع `ban`)
- ترتيب جديد للفرع: **تنفيذ الحظر أولاً** ← ثم تنبيه العضو ← ثم `force_logout`.
- `force_logout` يُبَث إلى غرفة `user:<id>` كاملة (كل أجهزة/تابات العضو) بدلاً من سوكيت واحد فقط.
- رسالة القائمة تعرض للمشرف أي معرفات حُظرت: (الاسم / IP / بصمة الجهاز).
- إعداد `expires_at` غير موجود → حظر دائم حقيقي.

### 3.3 نقاط الفرض (لا تغيير — موجودة وتعمل)
تلقائياً بعد كتابة السجلات، كل من: تسجيل دخول، دخول زائر، تسجيل عضوية، اتصال سوكيت سيرفض
فوراً برسالة الحظر من `banCheck` (فحص OR على: الاسم OR IP OR بصمة OR توقيع).
