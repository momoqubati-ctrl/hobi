## نظرة عامة

تنفيذ مسار الإرسال الخادمي للإعلانات، مع استهداف الأعضاء المتصلين وفق صلاحياتهم وعضويتهم الحالية، واحتساب الحصة بالتزامن الآمن، وحفظ التسليمات غير المغلقة، ثم بثها إلى قنوات المستخدمين الخاصة. لا تشمل الخطة زر الإرسال أو نموذج المستخدم أو تصميم شريط الإعلان؛ تلك ضمن وحدة التجربة التالية.

## القرارات المعمارية

- استخدام `getUserAuthContext` لاستخراج هوية الجلسة الموثقة ومنع جلسات الضيوف، وعدم قبول هوية المرسل من جسم الطلب.
- إضافة جداول منفصلة لبيانات الإعلان والمستلمين وحصة اليوم ومفاتيح منع التكرار. يحفظ نص الإعلان حتى إغلاق آخر تسليم، ثم يحذف المحتوى؛ تحتفظ بيانات الحصة وسجل منع التكرار ببياناتهما غير النصية اللازمة.
- إضافة ترحيل مخطط إضافي آمن للتكرار، وتسجيله في مسار إعداد قاعدة البيانات الحالي. لا تُشغّل ترحيلات حقيقية ضمن هذه الخطة.
- حل سياسة الإرسال من تعيينات الرتب النشطة وصلاحيات كل رتبة: اتحاد أنواع الإعلانات، وأكبر حد من الرتب التي تمنح نوعًا. يستثنى مالك النظام الموثق بسقف 10000 يوميًا، ولا يتغير حد الرتب العادي 0–1000.
- بناء قائمة الجمهور من خدمة الحضور الحالية. تُستبعد حسابات الضيوف وتزال تكرارات حساب المستخدم حتى لو ظهرت له عدة مقابس. جمهور `ranked` يتطلب رتبة فعالة غير افتراضية، أما `room` فيستخدم معرف الغرفة canonical وعضوية لحظة الإرسال.
- استخدام معاملة `PoolClient` واحدة لحجز مفتاح الطلب، وفحص/زيادة عداد المستخدم لليوم، وإنشاء سجل الإعلان والتسليمات. يضمن قفل PostgreSQL أن الطلبات المتزامنة لا تتجاوز الحصة أو تنشئ إرسالًا مكررًا.
- بث `announcement:created` عبر `publishUserEvent` إلى غرف `user:<id>` بعد نجاح المعاملة، وبث الإغلاق للمستلم. لا يُستخدم بث عام. تبقى قاعدة بيانات التسليمات المعلقة مصدر الاسترجاع عند إعادة الاتصال.
- تعيد API عناصر المستلم بترقيم cursor، وتحصر الإغلاق بحساب المستلم وتجعل تكراره آمنًا.
- تقسيم التنفيذ إلى أساس التخزين والسياسة/الجمهور، ثم مسار الإرسال، ثم الاسترجاع والإغلاق. لا يبدأ التنفيذ قبل اعتماد الخطة وقائمة المهام.

## مخطط الاعتماد

```text
مخطط التخزين ───────────────┐
سياسة المرسل ────────────────┼── خدمة الإرسال الذرية ── API الإرسال
حل الجمهور والرتب ───────────┘                      ├── بث Socket.IO للمستلمين
                                                   └── API القائمة والإغلاق
```

تعتمد سياسة المرسل على وحدة `announcement-permissions` المكتملة برمجيًا. لا يتوقف تنفيذ الخدمة على مراجعة الواجهة المرئية؛ فهذه المراجعة ما زالت متعذرة بسبب شهادة HTTPS المحلية.

## مراحل التنفيذ ونقاط التحقق

### المرحلة 1: الأساس

- مخطط الإعلانات والتسليمات وعدّاد الحصة ومفتاح منع التكرار مع ترحيل إضافي واختبارات المخطط.
- محلل سياسة المرسل وحدود الرتب ومالك النظام، مع اختبارات الصلاحيات والحصة والتاريخ المحلي.
- محلل الجمهور للجميع والسوابر والغرفة، مع اختبارات الحضور والرتبة الافتراضية والضيف وتكرار المقابس.

### نقطة تحقق: الأساس

- مخطط الإضافة قابل لإعادة التشغيل ولا يغيّر بيانات الجداول الحالية.
- لا يدخل أي عضو في جمهور السوابر بسبب الرتبة الافتراضية وحدها.
- حدود الأنواع والحصة، بما فيها استثناء المالك، مغطاة باختبارات خدمة.

### المرحلة 2: الإرسال

- خدمة إرسال واحدة تتحقق من السياسة، وتثبت الطلب والحصة والتسليمات في معاملة ذرية، وتعيد إيصالًا ثابتًا عند إعادة الطلب بنفس المفتاح.
- مسار `POST /api/announcements` يوثق الجلسة والمدخلات ويعيد رموز الأخطاء المتفق عليها.
- بث الحدث الخاص بالمستلمين بعد تثبيت المعاملة؛ لا تُبث بيانات الإعلان لقنوات غير مستهدفة.

### نقطة تحقق: الإرسال

- الطلب غير المصرح به أو المتجاوز للحصة لا ينشئ إعلانًا ولا تسليمًا.
- الجمهور الفارغ يستهلك حصة واحدة ويعيد عدد مستلمين صفرًا.
- إعادة الطلب المطابق لا تستهلك حصة أو تنشئ تسليمًا إضافيًا، والمفتاح بحمولة مختلفة مرفوض.

### المرحلة 3: الاسترجاع والإغلاق

- مسار `GET /api/announcements` يعيد قائمة المستخدم المعلقة مع cursor.
- مسار `DELETE /api/announcements/:id` يغلق تسليم المستخدم فقط، ويزيل محتوى الإعلان بعد إغلاق آخر مستلم.
- اختبار التزامن بين الإرسال والإغلاق وعزل حسابات المستلمين.

### نقطة تحقق: إكمال الوحدة

- تنجح `npm test` و`npm run build` وESLint للملفات الجديدة/المتغيرة دون أخطاء سببها هذه الوحدة.
- تُختبر دورة الإرسال، البث الخاص، التحديث، والإغلاق؛ لا يتضمن التنفيذ واجهة المستخدم بعد.
- لا يطبق ترحيل على قاعدة بيانات حقيقية.

## المخاطر والتخفيف

| الخطر | الأثر | التخفيف |
|---|---|---|
| اختلاف معرّف الغرفة أو وجود مقابس متعددة للحساب | جمهور ناقص أو مكرر | استخدام `resolveRoomId`، وتوحيد المستلمين بمعرف الحساب، واختبار الغرف ذات المعرفات البديلة |
| رتبة العضو الافتراضية تؤهل جميع الأعضاء خطأً | إفشاء إعلان السوابر للجميع | اشتراط رتبة نشطة غير افتراضية والتحقق من `starts_at` و`expires_at` |
| طلبات متزامنة تتجاوز الحصة | إرسال فوق حد السياسة | قفل ومعاملة PostgreSQL وعدّاد يومي ذري، واختبار تزامن |
| استثناء مالك النظام يُمنح لحسابات أخرى | تجاوز غير مصرح للحصة | تحقق متزامن من اسم مالك النظام وتعيين رتبة `is_owner` النشطة؛ اختبار سلبي للحسابات الأخرى |
| تعطل Socket.IO بعد حفظ الإعلان | لا يظهر فورًا لمتصل رغم بقاء التسليم | تسجيل فشل البث بوضوح؛ حفظ التسليم أولًا وإتاحته عبر API عند إعادة الاتصال، وإعادة بث العناصر المعلقة عند إعادة الطلب بالمفتاح نفسه |
| حجم جمهور كبير | ضغط Redis/Socket.IO | بث إلى غرف المستخدمين الخاصة بدفعات محدودة، وعدم استخدام القناة العامة أو إطلاق مهام غير محدودة بالتوازي |
