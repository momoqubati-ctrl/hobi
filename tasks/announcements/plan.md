# خطة التنفيذ: صلاحيات الإعلانات (`announcement-permissions`)

**الحالة:** التغييرات مطبقة؛ بقي التحقق المرئي وبعض فحوصات الأساس  
**المواصفة المعتمدة:** [SPEC-announcement-permissions.md](../../SPEC-announcement-permissions.md)  
**خريطة القدرات:** [CAPABILITY-MAP-announcements.md](../../CAPABILITY-MAP-announcements.md)

## نظرة عامة

إضافة صلاحيات إرسال الأنواع الثلاثة إلى مصفوفة الرتب، وإعداد حد يومي إجمالي لكل رتبة، ثم إظهار هذه السياسة وحفظها عبر واجهات إدارة الرتب الحالية. تقتصر هذه الوحدة على الإدارة والتخزين؛ التحقق وقت الإرسال والبث والواجهة الموجهة للمستخدم ضمن وحدات لاحقة.

## حالة التحقق

- نجح `npm test` (167 اختبارًا، 166 ناجحًا، لا إخفاقات، واختبار واحد متخطى) و`npm run build`.
- نجح ESLint للملفات المركزة الخالية من مشكلات الأساس. فحص بعض الملفات المعدلة الأخرى ما زال يعرض مشكلات lint سابقة في ملفاتها؛ لم تُجرَ إصلاحات خارج نطاق الوحدة.
- فحص TypeScript للملفات المتغيرة لم يعرض أخطاء مباشرة فيها، لكنه توقف عند خطأين سابقين في `permissionEngine.ts` و`redis.ts`، كما يحتوي فحص التطبيق الكامل على أخطاء سابقة في ملفات أخرى.
- تعذر الفحص المرئي لأن المتصفح المدمج رفض شهادة HTTPS المحلية ذاتية التوقيع؛ استجاب خادم التطوير محليًا بـ HTTP 200 عبر `curl`.
- لم يُنفذ ترحيل على قاعدة بيانات حقيقية.

## القرارات المعمارية

- استخدام صلاحيات منفصلة بصيغة `use` لأن كل نوع يمنح فعلًا واحدًا مستقلًا: `announcement_all.use` و`announcement_ranked.use` و`announcement_room.use`.
- استبعاد صلاحيات الإعلانات صراحةً من صلاحيات الأعضاء الافتراضية.
- تخزين الحصة في عمود `roles.announcement_daily_limit` مستقل عن مفاتيح `role_permissions` المنطقية، بقيمة افتراضية صفر وقيد من 0 إلى 1000.
- تمديد طلب مصفوفة الصلاحيات بحقل اختياري للحصص اليومية، مع التحقق من القيم ومعاملة قاعدة بيانات واحدة لحفظ الصلاحيات والحصص معًا.
- الاحتفاظ بواجهات API القديمة المتوافقة مع الطلبات التي لا ترسل الحصص.
- ترحيل مخطط إضافي قابل لإعادة التشغيل. لن يُطبّق على قاعدة بيانات حقيقية ضمن هذه الخطة.
- الحفاظ على جميع التغييرات الموجودة في مساحة العمل ودمج التعديلات عند لمس الملفات المتغيرة.

## مخطط الاعتماد

```text
تعريف صلاحيات الأنواع ─────────┐
                                ├── واجهات قراءة/حفظ سياسة الدور ── واجهة مصفوفة الصلاحيات
حقل الحصة والترحيل ────────────┘
```

## المهام

التفاصيل ومعايير القبول وخطوات التحقق في [قائمة المهام](./todo.md).

### المرحلة 1: قواعد الصلاحيات والتخزين

- `announcement-permission-keys`
- `announcement-role-limit-schema`

### نقطة تحقق: الأساس

- صلاحيات الأنواع مستقلة ولا تُمنح افتراضيًا.
- مخطط الحصة يفرض القيمة الافتراضية والنطاق المطلوب دون تنفيذ ترحيل على قاعدة غير اختبارية.

### المرحلة 2: واجهات الإدارة

- `announcement-policy-api`
- `announcement-policy-editor`

### نقطة تحقق: إكمال الوحدة

- يمكن للمسؤول المصرح له إعداد صلاحيات الأنواع والحصة لكل رتبة وحفظها وقراءتها.
- ترفض API الحصة غير الصحيحة ولا تحول قيمتها العددية إلى صلاحية.
- تنجح اختبارات المشروع والبناء وESLint للملفات المعدلة.
- مراجعة حقل الحصة في الواجهة ما زالت معلقة إلى حين إتاحة فحص مرئي عبر شهادة محلية موثوقة.

## المخاطر والتخفيف

| الخطر | الأثر | التخفيف |
|---|---|---|
| احتساب صلاحيات الإعلان ضمن صلاحيات الأعضاء الافتراضية | إرسال غير مقصود من أعضاء عاديين | اختبار صريح لعدم وجود مفاتيح الإعلان في مجموعة الافتراضيات |
| حفظ المصفوفة والحصة على اتصالين مختلفين | حالة رتبة جزئية بعد فشل الحفظ | تنفيذ التحديثين ضمن معاملة واحدة باستخدام `PoolClient` |
| اختلاف مخطط قاعدة البيانات الحالية عن مخطط Drizzle | فشل التشغيل بعد النشر | ترحيل إضافي قابل لإعادة التشغيل، واختبار مخطط دون تشغيله على قاعدة حقيقية |
| التغييرات المحلية غير المحفوظة في الملفات ذاتها | فقد عمل قائم | قراءة ودمج المحتوى الموجود، وعدم التراجع عن أي تغييرات غير هذه المهمة |
