**خريطة القدرات:** [CAPABILITY-MAP-site-owner.md](../../CAPABILITY-MAP-site-owner.md)  
**قائمة المهام:** [todo.md](./todo.md)

## النطاق

تنفيذ الوحدة `site-owner-bootstrap` فقط: إنشاء حساب العضوية ومجموعة صلاحيات التطبيق المحمية وإسنادها بصورة آمنة ومتكررة عند بدء التطبيق. لا تشمل هذه الخطة إسناد محفظة الموقع أو تغيير واجهة عرض الرصيد؛ فذلك ضمن الوحدة التالية `site-wallet-access` ويتطلب مواصفة وخطة مستقلتين.

## القرارات المعمارية

- نستخدم هوية ودورًا نظاميين مستقلين عن `safarihost` و`__system_owner__`، مع اسم دخول مضبوط في البيئة واسم عرض `مالك الموقع`.
- نستخدم تجزئة scrypt بالتنسيق القائم (`salt:hash`)؛ لا نحفظ كلمة مرور صريحة ولا نولّد اعتمادًا افتراضيًا.
- يتعامل bootstrap مع الإعدادات الناقصة/غير الصالحة على أنها تعطيل صريح لميزة مالك الموقع فقط، مع استمرار بقية التطبيق. أما فشل قاعدة البيانات أو تعارض اسم المستخدم مع حساب غير مملوك للنظام فيسجّل بوضوح ولا ينشئ هوية جزئية.
- تكون عملية إنشاء الحساب والدور والمنح والإسناد والملف الشخصي ذرّية وقابلة لإعادة التشغيل، ولا تستبدل كلمة مرور قائمة.
- مصدر صلاحيات الدور هو `RESOURCE_ACTIONS` في محرك الصلاحيات؛ يستبعد فقط مفتاح/صلاحية نافذة مالك الاستضافة وأي صلاحيات خاصة بهويته. يبقى الدور الجديد `is_owner = false` ولا يمنح جلسة مالك الاستضافة.
- تُحمى هوية الدور ومنحُه في واجهات الإدارة، وتُضاف حماية قاعدة بيانات من التعديلات والحذف العرضي. المالك الأعلى لقاعدة البيانات يظل قادرًا بطبيعته على تجاوز أي trigger؛ لذلك لا ندّعي عزلًا عن مسؤول قاعدة البيانات أو superuser.
- يجب حجز اسم المستخدم المضبوط من التسجيل العام، ورفض ترقية حساب سابق غير مملوك إلى حساب النظام بصمت.
- تستخدم تهيئة الخادم الحالية بعد اكتمال المخطط نقطة bootstrap واحدة، مع مسح/إبطال كاش صلاحيات العضو بعد نجاح التغيير.
- لا تُجرى أي كتابة إلى قاعدة إنتاج، ولا تُنشأ أرصدة أو معاملات دفتر أستاذ، ضمن هذه الخطة.

## المهام

### المرحلة 1: حدود الهوية والإعدادات

- [ ] المهمة `site-owner-config`: تعريف ثوابت/هوية مالك الموقع والتحقق من إعدادات username وscrypt hash وحجز الاسم من التسجيل العام.
- [ ] المهمة `site-owner-bootstrap`: إنشاء الحساب والدور والمنح والإسناد والملف الشخصي داخل معاملة ذرية متكررة آمنة.

### نقطة تحقق: التأسيس

- [ ] اختبارات الإعداد الناقص/الخاطئ وتعارض اسم الدخول تثبت عدم إنشاء سجلات جزئية.
- [ ] اختبار إعادة التشغيل يثبت عدم تكرار السجلات وعدم تغيير تجزئة كلمة مرور موجودة.
- [ ] لا توجد أي كتابة إلى أرصدة المستخدمين أو دفتر الأستاذ.

### المرحلة 2: حماية مجموعة الصلاحيات

- [ ] المهمة `site-owner-role-api-guards`: منع واجهات الإدارة من تعديل/تعطيل/حذف الدور المحمي أو تغيير منح صلاحياته، مع المحافظة على سلوك الأدوار العادية.
- [ ] المهمة `site-owner-role-db-guard`: إضافة حماية DB للمجموعة النظامية والتحقق من أن bootstrap/migrations المعتمدة فقط تحدّث قائمة صلاحياتها.

### نقطة تحقق: الحماية

- [ ] اختبارات API تغطي التعديل والحذف وتغيير المنح، مع إثبات استمرار العمليات على الأدوار العادية.
- [ ] اختبارات المخطط تثبت وجود الحماية ونجاح تحديثات bootstrap المصرح بها دون إزالة حماية الدور.
- [ ] لا يحصل الدور على `is_owner` أو صلاحية نافذة مالك الاستضافة.

### المرحلة 3: التهيئة والتكامل

- [ ] المهمة `site-owner-startup`: استدعاء bootstrap بعد تهيئة المخطط، تسجيل فشل إعداد الميزة دون تعطيل بقية التطبيق عند غياب الإعداد، وإبطال كاش الصلاحيات.
- [ ] المهمة `site-owner-final-verification`: التحقق من تسجيل الدخول العادي، نطاق الصلاحيات، التكرار، وعدم تأثر `safarihost`، ثم تشغيل الاختبارات والبناء وlint.

### نقطة تحقق: الإكمال

- [ ] ينشأ حساب واحد نشط بدور واحد محمي عند وجود إعدادات صحيحة.
- [ ] يسجل الحساب دخوله من مسار الأعضاء المعتاد ولا يحصل على سياق hosting-owner.
- [ ] الإعداد الناقص يعطل ميزة مالك الموقع بوضوح فقط، بينما يستمر التطبيق في خدمة بقية الوظائف.
- [ ] تنجح الاختبارات المركزة و`npm test` و`npx tsc --noEmit` و`npm run build` وESLint للملفات ذات الصلة.
- [ ] لا تُطبق ترحيلات إنتاج ضمن هذه الخطة.

## المخاطر والمعالجة

| الخطر | الأثر | المعالجة |
|---|---|---|
| اسم المستخدم المضبوط مستخدم مسبقًا بواسطة عضو آخر | تصعيد صلاحيات إلى حساب غير مقصود | رفض bootstrap بوضوح والتراجع الكامل؛ لا تغيير كلمة مرور أو دور الحساب الموجود |
| تشغيل أكثر من نسخة من التطبيق في الوقت نفسه | تكرار الحساب/الدور/المنح | قفل PostgreSQL استشاري ومعرّفات/فهارس فريدة وإدخالات idempotent |
| تحديث كتالوج الصلاحيات مستقبلًا | دور المالك يفقد صلاحيات جديدة أو يحصل على مفاتيح بوابة | توليد المنح من `RESOURCE_ACTIONS` مع اختبار استثناءات صريح |
| مسار API ثانوي يعدّل الأدوار أو المنح | تجاوز حماية صفحة إدارة الأدوار | حصر جميع نقاط الكتابة وإضافة اختبارات رفض على كل مسار |
| اعتبار حماية trigger عزلًا عن superuser | ضمان أمني غير صحيح | توثيق حد الحماية: تمنع التغيير العرضي/العادي ولا تحمي من مسؤول قاعدة البيانات |
| أسرار `.env` المحلية أو الإنتاجية | تسريب اعتماد مالك الموقع | بقاء `.env` محليًا مستثنى من Git؛ لا تُطبع التجزئة ولا تدخل حزمة العميل |

## خارج النطاق

- ربط `site_inventory` بحساب العضوية أو تغيير نوع الحساب المالي من system إلى member.
- تحديد من يرى رصيد محفظة الموقع أو سجلاتها، أو بناء صفحات المحفظة.
- تمويل المحفظة، backfill الأرصدة القديمة، محفظة الوكلاء، أو أي معاملة مالية.
- منح حساب مالك الموقع صلاحيات بوابة مالك الاستضافة.
- تطبيق تغييرات schema أو بيانات على قاعدة الإنتاج.

## البوابات

- اعتماد المستخدم لهذه الخطة مطلوب قبل بدء التنفيذ.
- أي ترحيل مخطط أو تشغيل على قاعدة إنتاج يحتاج موافقة صريحة مستقلة بعد مراجعة نطاقه.
