# قائمة مهام: تأسيس عضوية مالك الموقع

المواصفة: [SPEC-site-owner-bootstrap.md](../../SPEC-site-owner-bootstrap.md)  
الخطة: [plan.md](./plan.md)

## المرحلة 1: الهوية والإعدادات

- [x] **site-owner-config — تعريف الهوية والتحقق من إعدادات bootstrap**
  - القبول: إضافة اسم الدور/الحساب النظامي واسم العرض؛ التحقق من `SITE_OWNER_USERNAME` و`SITE_OWNER_PASSWORD_HASH` بتنسيق scrypt الحالي؛ عدم تسجيل القيم أو التجزئة.
  - القبول: حجز اسم الدخول العام ورفض التسجيل به؛ رفض تعارضه مع حساب سابق دون تعديله.
  - التحقق: اختبارات إعدادات صحيحة/ناقصة/خاطئة، username محجوز، وتعارض مستخدم.
  - الملفات المتوقعة: `server/services/systemOwner.ts`, `server/services/siteOwnerBootstrap.ts`, `server/services/authService.ts` أو خدمة التسجيل ذات الصلة، `server/routes/api/auth/register.post.ts`, `.env.example`, اختبارات مركزة.
  - الاعتماديات: لا يوجد.

- [x] **site-owner-bootstrap — إنشاء حساب المالك ومجموعته ذريًا**
  - القبول: إنشاء حساب عرض اسمه `مالك الموقع` ودور نظامي مستقل عن `safarihost`، مع ملف شخصي وإسناد دور، داخل معاملة واحدة.
  - القبول: إسناد جميع مفاتيح `RESOURCE_ACTIONS` الخاصة بالتطبيق ما عدا صلاحية نافذة مالك الاستضافة؛ عدم تعيين `is_owner` وعدم لمس أي رصيد.
  - التحقق: اختبار نجاح bootstrap، التراجع عند الفشل، إعادة التشغيل، عدم استبدال كلمة المرور، وعدم منح صلاحية hosting-owner.
  - الملفات المتوقعة: `server/services/siteOwnerBootstrap.ts`, `server/db/migrate.ts`, `server/services/permissionEngine.ts` عند الحاجة لتصدير مرشح الصلاحيات، `tests/siteOwnerBootstrap.test.ts`.
  - الاعتماديات: `site-owner-config`.

## نقطة تحقق: التأسيس

- [x] لا ينتج إعداد ناقص أو فشل معاملة سجلات جزئية.
- [x] لا يستطيع تسجيل الأعضاء أو الزوار حجز اسم الحساب المحمي.
- [x] إعادة تشغيل bootstrap لا تكرر الهوية ولا تغيّر كلمة المرور ولا الأرصدة.

## المرحلة 2: حماية الدور والمنح

- [x] **site-owner-role-api-guards — حماية مسارات إدارة الدور**
  - القبول: رفض تحديث/تعطيل/حذف الدور المحمي وتغيير منح صلاحياته من كل واجهات الإدارة.
  - القبول: تستمر إدارة الأدوار العادية كما كانت.
  - التحقق: اختبارات API لكل مسار كتابة مع حالات حماية الدور والأدوار العادية.
  - الملفات المتوقعة: `server/routes/api/admin/roles.put.ts`, `server/routes/api/admin/roles/[id].delete.ts`, مسارات/خدمات تحرير منح الصلاحيات التي تحددها مراجعة الاستدعاءات، اختبارات API ذات الصلة.
  - الاعتماديات: `site-owner-config`, `site-owner-bootstrap`.

- [x] **site-owner-role-db-guard — إضافة حاجز قاعدة البيانات**
  - القبول: منع تحديث الهوية المحمية وحذف الدور أو منح صلاحياته من مسارات SQL العادية، والسماح لتحديثات bootstrap المعتمدة فقط.
  - التحقق: اختبارات SQL/اختبارات fake للـtrigger، اختبار bootstrap بعد إضافة الحماية، وإثبات أن حذف الدور المحمي يُرفض.
  - الملفات المتوقعة: `server/db/migrate.ts`, `server/db/schema.ts` إن كان هناك تعريف schema معتمد، `tests/siteOwnerBootstrap.test.ts`.
  - الاعتماديات: `site-owner-bootstrap`.

## نقطة تحقق: الحماية

- [ ] جميع مسارات الإدارة التي تكتب الأدوار أو المنح حُصرت واختُبرت.
- [x] الدور ليس `is_owner` ولا يحتوي صلاحية نافذة مالك الاستضافة.
- [x] حدود الحماية من مسؤول قاعدة البيانات موثقة ولا تُسوّق كحماية ضد superuser.

## المرحلة 3: التهيئة والتحقق

- [x] **site-owner-startup — ربط bootstrap بتهيئة التطبيق**
  - القبول: بعد تهيئة المخطط، يُشغّل bootstrap مرة واحدة لكل عملية بدء وبشكل آمن بين النسخ المتوازية.
  - القبول: عند غياب/فساد الإعداد، يسجل خطأ إعدادًا واضحًا ويعطّل ميزة المالك فقط؛ بقية التطبيق تستمر. عند فشل قاعدة البيانات لا تُخفى أخطاء التهيئة.
  - القبول: إبطال كاش صلاحيات الحساب بعد نجاح إنشاء الإسناد أو تحديث المنح.
  - التحقق: اختبارات plugin/bootstrap وأوضاع الإعداد والفشل، ثم فحص سجلات الاختبار لعدم تسرب التجزئة.
  - الملفات المتوقعة: `server/plugins/database.ts`, `server/services/siteOwnerBootstrap.ts`, `tests/siteOwnerBootstrap.test.ts`.
  - الاعتماديات: `site-owner-bootstrap`, `site-owner-role-api-guards`, `site-owner-role-db-guard`.

- [x] **site-owner-final-verification — التحقق النهائي**
  - القبول: العضو يستخدم مسار الأعضاء العادي؛ صلاحياته هي صلاحيات التطبيق فقط؛ `safarihost` يظل منفصلًا دون تغييرات.
  - التحقق: الاختبارات المركزة، `npm test`, `npx tsc --noEmit`, `npm run build`, وESLint للملفات المعدّلة.
  - القبول: توثيق أي تعثر سابق أو غير مرتبط، دون تعطيل الاختبارات أو خفض معاييرها.
  - الملفات المتوقعة: ملفات التنفيذ والاختبارات؛ لا تعديل على `.env` الحقيقي ولا نشر/ترحيل إنتاج.
  - الاعتماديات: `site-owner-startup`.
  - نتيجة التحقق: `npm test` (256/256 بعد إعداد `.env`)، `npx tsc --noEmit`، و`npm run build` نجحت؛ ESLint ما زال يرصد مخالفات قديمة في الملفات المعدّلة، ولا تقع ضمن أسطر التغيير.
  - نتيجة الإنتاج: قاعدة `chat_app` تحتوي حسابًا واحدًا ودورًا محميًا وملفًا شخصيًا وإسنادًا واحدًا؛ تطابق هاش الاعتماد المهيأ؛ المنح الـ357 مطابقة لصلاحيات التطبيق، دون منح `hosting_owner.*`.

## نقطة تحقق: الإكمال

- [x] جميع معايير مواصفة `site-owner-bootstrap` متحققة في الكود والاختبارات.
- [x] لم تُربط محفظة الموقع بهذه العضوية ولم يتغير أي رصيد؛ ذلك ضمن الوحدة اللاحقة.
- [x] تهيئة الإنتاج تمت بعد تفويض المستخدم، والتحقق من وجود حاجزي حماية الدور والمنح قبل التأسيس.

> ضُبط `SITE_OWNER_USERNAME` وهاش scrypt لكلمة المرور في `.env` المحلي المستثنى من Git. لا تُعرض بيانات الاعتماد أو الهاش في السجلات أو التقارير.
